# 工作文档

## 1 任务描述

- 本项目旨在完成一套基于 GRPO 方法的大模型后训练的 python 实现，使用 Hugging Face 生态，基于 Lora 方法实现高效参数微调。
- 项目需包含大模型训练脚本、大模型评估脚本、配置文件、示例数据集、工具脚本。
- 训练及评估脚本需要能够直接在本地 Windows 电脑上的名为 cuda118env 的 conda 环境下使用 python 命令直接运行。
- 评估脚本需要能够 Linux 系统的服务器容器上使用 python 命令直接运行。
- 训练脚本需要能够 Linux 系统的服务器容器上使用 accelerate 命令运行，当显卡数量大于 1 时采用数据分片。
- 所有和环境相关的名称不能暴露在代码和数据集中。

## 2 目录结构

- 根目录`./`下： 训练及评估配置文件（Config.yaml）、accelerate配置文件（accelerate_config.yaml）、训练脚本（train.py）、工具脚本（tool_grpo.py）、奖励函数脚本（reward_function.py）、模型评估脚本（evaluate_model.py）、训练过程绘制脚本（plot.py）
- 示例数据集目录`./example_data/`下： 示例训练数据集文件（data_train.jsonl）、示例测试数据集文件（data_test.jsonl）。
- 输出目录`./output/`下： 所有脚本产生的输出、过程文件、临时文件都放置在这个文件夹下特定的子目录（如 logs/、checkpoints/、final_model/、eval/、plots/ 等）。

## 3 任务要求

1. 训练及评估配置文件（Config.yaml）：
	- 所有在模型及数据集读取、训练、保存、评估等过程中需要修改的超参数、模型及数据集目录、训练配置等设置项全部暴露于本文件中，其余文件从本文件读取来获得。
	- 所有设置项按功能及过程的区别分类为不同的命名对象，利于人类阅读和修改。
	- 每个命名对象和具体配置项需配有注释说明用途。
	- Hugging Face 库中的训练器（trainer）类的配置项单独使用一个命名对象 TrainConfig 来定义，在训练脚本中读取为一个字典对象，并使用`train_args = GRPOConfig(**TrainConfig, ... )`方式直接整体传入。以保持本配置文件和训练器配置项输入参数的格式统一。
	- 数据集配置中需要包含训练数据集和测试数据集的路径。
	- 数据集配置中需要分别指定训练数据集和测试数据集中数据的使用率，默认为1，即使用数据集文件中100%的样本。
	- 数据集配置中需要指定验证集的占比，后续将按照这个比例从指定的训练数据集中划分训练集和验证集。
2. accelerate配置文件（accelerate_config.yaml）：
	- 需支持在海光服务器的 DCU 显卡上运行。
	- 服务器为1台机器4张显卡。
3. 训练脚本（train.py）：
	- 仅有一个主函数，其余函数、类、工具等定义放到工具脚本（tool_grpo.py），保持代码简洁。
	- 主函数内按步骤组织代码，各步骤需包含详细的注释。
	- 自定义训练器的训练时的日志回调类，训练时打印过程信息，并保存为训练过程jsonl文件，保存路径为输出目录下的子文件夹。
	- 每次训练的日志jsonl都单独保存为一个文件，文件名中附带上训练时间（如 `train_log_20260902_115858.jsonl`）。
	- 同时维护一个统一的当前训练日志接口文件 `train_log.jsonl`：训练每一步结束后，先追加写入时间戳日志文件，再将 `train_log.jsonl` 的内容同步为与时间戳日志文件完全一致（即清空后重写），使得 `train_log.jsonl` 始终包含最新一次训练的完整日志。
	- 训练过程绘制脚本直接读取 `train_log.jsonl` 进行绘图，无需自动匹配最新文件。
	- 在训练开始和每轮epoch完成后都跑一次评估，即将训练器的"eval_strategy"设为"epoch"，将"eval_on_start"参数设为True。
	- 训练使用 Lora 方法，训练过程中和结束后需要能够自动保存模型和训练检查点，模型的保存方式均为保存 Lora 适配器，为了节省空间不要保存全部模型权重，保存路径为输出目录下的子文件夹。
	- 脚本运行时需要打印简洁明了的信息，所有打印信息保存风格统一。
	- 当脚本使用 accelerate 命令运行时，请注意协调主进程和其他进程之间功能，不要出现冗余操作、竞态操作等危险行为，例如多个进程都打印过程信息。
4. 工具脚本（tool_grpo.py）：
	- 所有其他脚本中的函数和类都在此文件中定义。
	- 所有其他脚本中能够实现封装的功能都在此文件中封装。
	- **注意**：奖励函数类（GRPORewardFunction）已移至独立的奖励函数脚本文件（reward_function.py）中，不在本文件中定义。工具脚本中不包含奖励函数相关代码。
5. 奖励函数脚本（reward_function.py）：
	- 该脚本专门用于实现 GRPO 奖励函数类（GRPORewardFunction），作为 GRPO 训练的核心驱动机制，通过 `reward_funcs` 参数传入 GRPOTrainer。
	- **类结构设计**：
		- `__init__`：初始化配置参数，包括各奖励分量的权重字典（`weights`）、答案提取标签（`answer_tag`）等。
		- `__call__`：GRPO Trainer 的调用入口，接收 `prompts`（列表）、`completions`（列表）、`references`（列表，可选）作为参数，返回奖励张量（torch.Tensor）。
		- 内部方法：实现答案提取、各分量奖励计算等独立逻辑。
	- **多组件加权奖励思想**：
		- 支持多个奖励分量，每个分量独立计算后通过权重字典加权组合得到总奖励。
		- 示例分量及权重（仅作为参考，具体任务需按需修改）：
			- **长度奖励**：衡量生成内容与参考答案长度的接近程度。计算公式：`reward = 1 - |len_gen - len_ref| / (len_gen + len_ref)`，值越接近 1 表示长度越匹配。
			- **文字匹配奖励**：衡量生成内容与参考答案首字符的一致性。若生成文本去除空白后的首字符与参考答案首字符相同，则奖励为 1.0，否则为 0.0。
		- 示例权重配置：`{'length': 0.5, 'match': 0.5}`，可根据具体任务需求灵活调整权重比例。
	- **奖励归一化与标准化**：
		- 各分量奖励应归一化到 [0,1] 范围，确保不同量纲的奖励可公平组合。
	- **参考回答（Reference）的使用**：
		- 支持传入参考回答（`references`），用于计算各分量奖励。
		- 奖励函数内部应维护一个 `rewards` 字典，存储各分量奖励、总奖励等中间结果，便于训练日志回调和评估脚本提取使用。
	- **批量处理与异常处理**：
		- 支持批量输入（batch），内部按样本逐个处理，返回批量奖励张量。
		- 对异常样本（如提取失败、计算错误）应有降级处理（如返回 0 奖励），不影响整体批量计算。
	- **与训练日志的协同**：
		- 奖励函数计算的 `rewards` 应被训练日志回调（如 `PerStepLogCallback`）在 `on_log` 时提取，注入到训练日志中。
		- 评估脚本应能从奖励函数实例中直接读取历史奖励数据，用于生成评估报告。
6. 模型评估脚本（evaluate_model.py）：
	- 该脚本作为一个例外，在该脚本内部实现大模型的评估函数和评估报告输出函数，并在主函数中调用，不用将函数放到工具脚本中；
	- 评估指标需要基于 GRPO 特性，包含平均奖励（avg_reward）、奖励标准差（reward_std）、Pass@k（pass@1 ~ pass@k）、平均语法错误数（avg_error_count）、零错误样本比例（zero_error_rate）、奖励分布统计（min/25%/中位数/75%/max）、奖励分项统计（syntax/length 的平均值与标准差）、每个 Prompt 的平均奖励标准差、生成速度（tokens/s）等。
	- 评估过程采用**分 Batch 并行生成策略**：为了实现高效的 Pass@k 计算并优化显存，评估函数会将每个 Prompt 复制 $N$ 次（$N$ 为每个 Prompt 生成数）构建成大 Batch 进行一次性推理，从而实现并行生成大量回答。
	- **奖励函数驱动评估**：评估逻辑紧密耦合奖励函数，通过对生成的回答进行批量打分，获取奖励分布、语法错误数等核心统计量。
	- **显存与模型适配**：评估逻辑需具备显存优化意识，支持 PEFT/LoRA 适配器的切换（使用 `set_adapter` 加载微调后的适配器），并能处理 Batch 推理过程中的 OOM 情况（遇到 OOM 时自动减小 Batch 并跳过）。
	- 该脚本的主函数包含两个步骤：基座模型、微调后模型评估。每次评估都调用评估函数完成，每次评估完成后都调用评估报告输出函数，将结果输出为输出目录下评估子文件夹下的 markdown 文件。
	- 评估函数的返回值为保存多个评估指标及评估结果的字典，并作为评估报告输出函数的输入参数，评估报告输出函数将评估指标及评估结果以规范的语言写入到 markdown 文件。
	- 待评估的大模型路径、测试数据集路径、是否评估基座模型、是否评估微调后模型等配置参数都放到训练及评估配置文件中，单独使用一个命名对象 EvalConfig 来定义。
	- 生成样例展示要求：在评估报告（markdown 文件）的生成样例部分，必须直接打印模型的原始输入和原始输出，即包含 system、user、assistant 等角色标签的完整文本（经过 `tokenizer.apply_chat_template` 渲染后的结果），不得只显示处理后的纯文本内容。这样可以在检查样例时直观看到模型接收到的完整 prompt 格式以及生成内容的完整上下文，便于排查数据格式、角色标签、生成截断等问题。模型输出中尾部多余的重复角色标签（如多个 "assistant"）仍需在后处理中 strip 掉，但角色标签前缀和正文内容必须完整保留。
7. 训练过程绘制脚本（plot.py）：
	- 该脚本位于项目根目录（与训练、评估脚本同级），用于绘制训练过程的可视化曲线，从训练器输出的训练过程jsonl文件中提取训练/评估指标，使用 matplotlib 库生成多子图训练曲线图。
	- 日志指标映射（param_mappings）包含：loss（对应 eval_loss）、grad_norm（无 eval）、learning_rate（无 eval）、completions/min_length（对应 eval_completions/min_length）、completions/mean_length（对应 eval_completions/mean_length）、completions/max_length（对应 eval_completions/max_length）、completions/clipped_ratio（对应 eval_completions/clipped_ratio）、reward（对应 eval_reward）、reward_std（对应 eval_reward_std）、mean_error（对应 eval_mean_error）、zero_ratio（对应 eval_zero_ratio）、kl（对应 eval_kl）、entropy（对应 eval_entropy）、step_time（无 eval，绘制累计耗时曲线）。
	- **双层曲线展示思想**：在启用采样平滑（`stride > 1`）时，采用"原始曲线做底，平滑曲线置顶"的视觉方案。使用极浅透明度（`alpha=0.2`）的原始数据作为背景，叠加较高透明度（`alpha=0.8`）的滑动窗口平均曲线，以便在观察整体趋势的同时保留原始波动信息。
	- **时间效率可视化**：针对 `step_time` 指标，采用**累计耗时（分钟）**的逻辑进行绘制，并在曲线末端自动标注训练的总时长与总步数，用于直观评估训练效率。
	- 绘制函数需要包含参数：子图列数、子图垂直间距、子图水平间距、总标题 Y 轴位置、从第几步开始绘制（跳过前 N 步）、采样步长（滑动窗口平滑）。从训练及评估配置文件读取。
	- 绘制的图像文件输出到输出目录下的 `plots/` 子文件夹。

## 6 注意事项

以下为 GRPO 训练脚本构建中的共性注意事项，适用于任意基座模型和任务场景。

### 6.1 训练

- **GRPO 数据格式中 messages 嵌套**：从 prompt 重建 messages 时注意不要多加一层嵌套（`[[{...}]]`），否则 `batched=True` 时 `msg_list[0]` 返回 list 而非 dict，导致 chat template 渲染失败。正确写法：`[{"role":"user",...}, {"role":"assistant",...}]`，assistant 内容为空占位。
- **TrainerCallback 兼容性**：自定义回调必须继承 `TrainerCallback` 基类，显式实现所有用到的钩子方法（`on_init_end`/`on_train_begin`/`on_train_end`/`on_log`/`on_evaluate`）。注意不同版本中 `Control` 类的导入路径可能变化。
- **GRPO batch size 约束**：`per_device_eval_batch_size` 必须能被 `num_generations` 整除，否则触发 `ValueError`。
- **tqdm 进度条干扰**：tqdm 在 stderr 上反复覆盖输出，会淹没 stdout 的训练过程日志。推荐禁用 tqdm 或使用静默包装类，同时保留模块结构（如 `thread_map`/`process_map`）以满足框架内部导入需求。
- **生成时 padding 方向**：decoder-only 架构生成时必须使用 `padding_side='left'`。训练阶段可用 `right` padding，但生成前需临时切换，否则影响生成质量。

### 6.2 配置与保存

- **LoRA 适配器保存**：训练结束后仅保存 LoRA 适配器（~几十 MB），不保存完整模型权重。部署时与基座模型合并加载即可。
- **训练元信息持久化**：每次训练结束后自动保存训练元信息文件（含起止时间、模型标识、样本数、LoRA 参数、训练参数等），用于训练复盘和复现。
- **Config 约束一致性**：`load_best_model_at_end: true` 要求 `save_strategy` 与 `eval_strategy` 匹配（同为 `"epoch"` 或 `"best"`）。错误组合会触发 `ValueError`。

### 6.3 评估

- **Pass@k 与 num_generations 的关系**：Pass@k 计算时 `k` 不能超过 `num_generations`（每个 prompt 的实际生成次数）。若 `k > num_generations`，Pass@k 的值会被低估。
- **生成时 OOM 处理**：批量推理时需捕获 `RuntimeError`（OOM），自动跳过当前 batch 并清理显存缓存，避免整个评估流程中断。

### 6.4 绘图

- **日志路径容错**：绘图脚本读取日志时，应兼容不同的输出目录结构（如根目录下和子目录下两种 log 路径），避免路径硬编码。
- **图例警告**：部分指标（如 `grad_norm`/`learning_rate`/`step_time`）无 eval 对应项，仅含单侧数据时 `ax.legend()` 会报 `No artists with labels found`，属正常现象可忽略。
- **绘图降采样**：训练步数较多时使用 `stride` 滑动窗口降采样。推荐"原始线 `alpha=0.2` + 平滑线 `alpha=0.8`"的双层视觉方案。
- **matplotlib 字体兼容**：避免使用系统中可能不存在的中文字体，改用通用字体（如 `DejaVu Sans`），确保跨平台渲染一致。
